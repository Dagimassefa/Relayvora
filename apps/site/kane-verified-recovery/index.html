Relayvora/Verified recovery with Kane

GUIDE / EXPERIMENTAL

Done means it works in the browser.

Coding agents often say “done” when the app is not. Relayvora starts your app from the exact source on disk, has Kane CLI test it in a real browser, and when Kane confirms a bug, hands Kane’s findings to Codex or Claude Code, restarts the app from the fix, and checks again.

relayvora recover runExperimental · relayvora 0.1.0-alpha.6+

Run it

Install Kane CLI and sign in, stop anything already using the app’s port, then from your project:

npm install -g relayvora @testmuai/kane-cli
kane-cli login --oauth

relayvora recover run --spec spec.md --protect test/app.test.js \
  --objective "Open http://localhost:3000/, delete an item with its Delete button, refresh, and verify it is gone" \
  --start "node server.mjs" --url http://localhost:3000/ \
  --check "npm test" --agents codex,claude --max-attempts 2

relayvora recover report

For a single check without repair, use relayvora gate run with the same options.

What happens

StepWhat Relayvora does
CheckFingerprints the source, refuses if the port is already taken, starts the app, points Kane at it and runs your regression checks.
BriefOn a confirmed defect, gives the next agent the objective, the locked spec, Kane’s verdict and step notes, failing check output and earlier attempts.
FixRuns the agent headlessly in the project: Codex in its workspace-write sandbox, Claude Code with acceptEdits. No permission bypasses.
RecheckRestarts the app from the new source and runs Kane and every check again, until verified or out of attempts.

A real run

On a small list app missing its Delete button: Kane failed it (“saved list items have no Delete button”, a confirmed product bug). Codex, the first agent, crashed on its model configuration and changed nothing; the recheck still failed. Claude Code, the fallback, added the button and a delete route. Kane then passed, the regression test passed, and the locked files were untouched: verified, in about five minutes. Read the full report ↗

Why you can trust “verified”

Relayvora only reports verified when Kane passed against the app it started itself from the fingerprinted source, every check passed, the app stayed up for the whole run, and nothing changed meanwhile. The spec, objective and protected tests are locked, so an agent cannot pass by rewriting them. Kane’s output is treated as evidence, never as instructions, and its suggestions are marked unverified.

Limits, stated plainly: ignored files, dependencies, environment and external services are outside the fingerprint; state files guard against accidents, not a hostile process running as you; and a first benchmark on this task found every approach succeeded, so it does not yet show when recovery wins. Questions

What does verified mean?+

Kane passed against the app Relayvora started from the fingerprinted source, every regression check passed, the app process stayed alive, and the source, spec and protected files did not change during the run. It covers the objective and checks you supplied, not requirements they leave out.

Can the fixing agent cheat by editing the spec or tests?+

The spec, the objective and any files passed with --protect are locked on the first run. If an agent changes them, the recovery stops as blocked. Tests you do not protect are not locked.

Does it give agents extra permissions?+

No. Codex runs with the workspace-write sandbox and Claude Code with acceptEdits. Relayvora never passes sandbox or permission bypass flags.

Is it available on npm?+

Yes, from relayvora 0.1.0-alpha.6: npm install -g relayvora. The gate and recover commands are experimental. You also need Kane CLI, signed in, and Codex or Claude Code for repairs.
